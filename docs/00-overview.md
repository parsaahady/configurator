# نمای کلی پروژه: سامانه تحت وب تنظیم و پخش زنده دوربین کوادکوپتر (XeroxUAV)

خوش آمدی! در این پروژه قرار است قدم‌به‌قدم، یک ماژول واقعی و استاندارد برای تیم کوادکوپتر **XeroxUAV** بسازیم: سامانه‌ای که تصویر دوربین روی رزبری‌پای را با **تأخیر کمتر از یک ثانیه** داخل مرورگر لپ‌تاپ نمایش می‌دهد و به تو اجازه می‌دهد بدون لمس ترمینال، تنظیمات دوربین را به‌صورت زنده تغییر بدهی.

در کار قبلی‌ات موفق شدی با **GStreamer** تصویر را از رزبری‌پای با **RTP/UDP** به لپ‌تاپ بفرستی؛ یعنی پایه‌های پایپ‌لاین GStreamer و مفاهیم پایه شبکه (IP، پورت، TCP و UDP) را بلدی. اینجا دیگر آن‌ها را تکرار نمی‌کنیم و فقط سراغ مفاهیم جدیدی می‌رویم که پروژه را از یک تست آزمایشگاهی به یک ابزار حرفه‌ای تبدیل می‌کنند.

---

## ۱. چرا به این سامانه نیاز داریم؟ (هدف پروژه)

در آزمایش قبلی، برای دیدن تصویر باید روی هر دو سیستم دستورهای طولانی در ترمینال می‌نوشتی. اگر وسط تست شبکه ضعیف می‌شد و می‌خواستی رزولوشن یا حجم تصویر را کم کنی، باید با SSH وارد رزبری‌پای می‌شدی، دستور قبلی را متوقف می‌کردی و دستور جدیدی اجرا می‌کردی. تازه مرورگرهای وب هم به دلایل امنیتی اجازه ندارند مستقیماً یک پورت خام UDP را باز کنند و ویدیو نشان بدهند!

هدف ما ساختن ماژول دوربین برای **ایستگاه کنترل زمینی تحت وب (Web Ground-Control Station یا GCS)** است؛ یعنی برنامه‌ای روی لپ‌تاپ که اپراتور تیم فقط با باز کردن مرورگر بتواند:

1. تصویر زنده دوربین را با تأخیر بسیار کم (زیر یک ثانیه) ببیند.
2. رزولوشن، نرخ فریم (FPS) و نرخ بیت (Bitrate) را از همان صفحه وب تغییر بدهد و تصویر خودش دوباره وصل شود.
3. آمار زنده سلامت تصویر و دمای پردازنده رزبری‌پای را لحظه‌به‌لحظه ببیند.

## ۲. قانون طلایی ایمنی و نردبان راستی‌آزمایی تیم

پیش از نوشتن حتی یک خط کد، دو قانون همیشگی تیم **XeroxUAV** را مرور می‌کنیم:

> **قانون طلایی ملخ‌ها (The Golden Propeller Rule):**
> در تمام مراحل توسعه نرم‌افزار، عیب‌یابی و تست روی میز کار (Bench Test)، **ملخ‌های کوادکوپتر باید به‌صورت فیزیکی باز و جدا شده باشند.** هرچند این پروژه روی میز فقط به رزبری‌پای و دوربین نیاز دارد، اگر رزبری‌پای روی پرنده بسته باشد، هرگز با ملخِ بسته باتری وصل نمی‌کنیم.

همچنین هیچ تغییری را مستقیم و چشم‌بسته روی سخت‌افزار نمی‌بریم، بلکه از **نردبان راستی‌آزمایی (Verification Ladder)** بالا می‌رویم:

1. **تست واحد و بررسی ایستا (Unit Tests & Static Analysis):** ابزارهای خودکار، غلط‌های تایپی، پیچیدگی کد و منطق برنامه را روی لپ‌تاپ بررسی می‌کنند (در حالی که دوربین و شبکه شبیه‌سازی یا به اصطلاح **Mock** شده‌اند).
2. **یکپارچه‌سازی مداوم (CI - Continuous Integration):** با هر بار ارسال کد به GitHub، یک سرور خودکار دوباره تمام تست‌ها و قوانین کدنویسی تیم را چک می‌کند تا کد خراب وارد پروژه نشود.
3. **تست روی میز کار (Bench Test):** اجرای واقعی با رزبری‌پای، دوربین و لپ‌تاپ روی میز کار (بدون ملخ!).

## ۳. مفاهیم پایه برای فهم نقشه کلی

در طول قدم‌های بعدی هر فناوری را عمیق و با مثال باز می‌کنیم، اما برای اینکه نقشه کلی زیر را کامل بفهمی، اول با ۶ بازیگر اصلی آن آشنا شویم:

- **فشرده‌سازی تصویر (`H.264`):** دوربین ما تصویر را به‌صورت خام (`YUY2`) تحویل می‌دهد؛ یعنی رنگ تک‌تک پیکسل‌ها را بدون هیچ فشرده‌سازی می‌فرستد که حجم فوق‌العاده زیادی دارد. `H.264` یک روش استاندارد فشرده‌سازی ویدیو است (مثل زیپ کردن هوشمند فیلم) که حجم داده را ده‌ها برابر کوچک می‌کند تا از شبکه عبور کند.
- **سرور رسانه (`MediaMTX`):** برنامه‌ای آماده و سبک روی لپ‌تاپ که نقش «ایستگاه پخش زنده» را دارد؛ ویدیو را از رزبری‌پای تحویل می‌گیرد و به فرمتی تبدیل می‌کند که مرورگر وب بتواند پخش کند.
- **پروتکل `RTSP`:** قرارداد استانداردی شبیه یک لوله اختصاصی ارسال ویدیو که GStreamer با کمک آن، ویدیوی فشرده‌شده را از رزبری‌پای به `MediaMTX` تحویل می‌دهد.
- **فناوری `WebRTC` و `WHEP`:** `WebRTC` همان فناوری تماس تصویری زنده در مرورگر است (مثل Google Meet) که برای کمترین تأخیر ممکن طراحی شده است. `WHEP` هم یک روش ساده و استاندارد برای شروع این ارتباط با سرور رسانه است (در قدم ۳ کامل کالبدشکافی‌اش می‌کنیم).
- **بک‌اند (`Backend`) و فرانت‌اند (`Frontend`):** به صفحه وب که داخل مرورگر می‌بینی **Frontend** و به برنامه پایتونی پشت‌صحنه روی لپ‌تاپ (که ما با فریم‌ورک **FastAPI** می‌سازیم) **Backend** می‌گویند.
- **پروتکل `WebSocket` و دستیار پای (`Pi-Agent`):** صفحه وب برای ارسال دستور «تغییر رزولوشن» و دریافت «دمای CPU» به یک خط تلفن دوطرفه و همیشه باز نیاز دارد که به آن **WebSocket** می‌گوییم. در سمت رزبری‌پای هم یک برنامه کوچک پایتونی به نام **Pi-Agent** می‌نویسیم که پای این خط تلفن نشسته و وظیفه‌اش روشن، خاموش و راه‌اندازی دوباره پایپ‌لاین GStreamer است.

## ۴. تصویر بزرگ معماری: جداسازی مسیر ویدیو و مسیر کنترل

مهم‌ترین تصمیم مهندسی این پروژه این است که **مسیر ویدیو** و **مسیر کنترل** را کاملاً از هم جدا نگه می‌داریم:

```text
  [رزبری‌پای ۴ - Raspberry Pi 4]                        [لپ‌تاپ ویندوز - Ground Station]
 ┌──────────────────────────────┐                     ┌──────────────────────────────────┐
 │                              │                     │                                  │
 │  دوربین Arducam (/dev/video1) │                     │            MediaMTX              │
 │          │ (خام: YUY2)       │   ۱. مسیر ویدیو     │         (سرور رسانه زنده)        │
 │          ▼                   │     RTSP (:8554)    │                │                 │
 │      GStreamer               │ ──────────────────► │                │ WebRTC (WHEP)   │
 │   (فشرده‌سازی به H.264)      │                     │                │ (:8889)         │
 │          ▲                   │                     │                ▼                 │
 │          │ (شروع / ری‌استارت) │                     │       ┌─────────────────┐        │
 │          │                   │   ۲. مسیر کنترل     │       │   مرورگر وب     │        │
 │      Pi-Agent                │ ◄─────────────────► │       │  (پخش + پنل     │        │
 │  (ناظر پایتونی + دمای CPU)   │     WebSocket       │       │   تنظیمات زنده) │        │
 │                              │         │           │       └────────▲────────┘        │
 └──────────────────────────────┘         │           │                │ HTTP / WS       │
                                          │           │                ▼                 │
                                          └─────────► │        Backend (FastAPI)         │
                                                      │     (مدیریت کانفیگ و ارتباط)     │
                                                      └──────────────────────────────────┘
```

**چرا ویدیو را از داخل پایتون رد نمی‌کنیم؟**
چون پردازش ده‌ها فریم ویدیو در ثانیه کار بسیار سنگینی است. GStreamer به زبان C نوشته شده و مستقیم فریم‌ها را با بالاترین سرعت به `MediaMTX` می‌فرستد. کد پایتون ما (`Backend` و `Pi-Agent`) اصلاً به پیکسل‌های ویدیو دست نمی‌زند؛ فقط مثل یک «مدیر صحنه» دستور شروع و تغییر تنظیمات را می‌دهد و آمار سلامت را می‌خواند. به همین خاطر حتی اگر مسیر کنترل لحظه‌ای شلوغ شود، تصویر زنده گیر نمی‌کند!

## ۵. معماری داخلی کد پایتون (معماری شش‌ضلعی / Hexagonal)

طبق استاندارد تیم **XeroxUAV**، تمام کد پروژه را در یک فایل شلوغ نمی‌ریزیم، بلکه آن را به ۴ لایه مرتب تقسیم می‌کنیم که وابستگی‌شان همیشه **از بیرون به سمت داخل** است:

```text
presentation (وب، FastAPI، پیام‌های شبکه)  ──┐
                                             ├──► application (هماهنگ‌کننده کارها) ──► domain (قوانین خالص هسته)
infrastructure (اجرای GStreamer، فایل، دما) ──┘
```

| لایه | نقش به زبان ساده | مثال در پروژه ما |
| :--- | :--- | :--- |
| **`domain/`** | مغز و قوانین خالص سیستم؛ هیچ اطلاعی از وب، شبکه یا لینوکس ندارد. | رزولوشن‌های مجاز دوربین، محدوده مجاز FPS و بیت‌ریت، تعریف قرارداد انکودر. |
| **`application/`** | مدیر اجرایی؛ قوانین هسته را برمی‌دارد و ترتیب انجام کارها را هماهنگ می‌کند. | بررسی درستی تنظیمات جدید، نظارت بر زنده بودن GStreamer و تلاش مجدد در صورت قطع شدن. |
| **`infrastructure/`** | دست‌وپاهای واقعی سیستم؛ با سیستم‌عامل، فایل و سخت‌افزار صحبت می‌کند. | اجرای واقعی دستور `gst-launch-1.0`، خواندن دمای CPU رزبری‌پای، ذخیره فایل تنظیمات. |
| **`presentation/`** | ویترین و درگاه ارتباط با کاربر و شبکه. | سرور FastAPI، پیام‌های WebSocket و فایل‌های HTML/CSS/JS صفحه وب. |

**فایده این کار چیست؟** اول اینکه می‌توانیم بدون وصل کردن دوربین واقعی، تمام منطق برنامه را روی هر لپ‌تاپی در کسری از ثانیه تست کنیم. دوم اینکه بعداً وقتی این پروژه را داخل نرم‌افزار بزرگ ایستگاه زمینی تیم ادغام کنیم، هسته برنامه بدون هیچ تغییری سر جایش کار می‌کند.

## ۶. واقعیت‌ها و محدودیت‌های محیط کار ما

طراحی ما دقیقاً بر اساس شرایط واقعی سخت‌افزار و شبکه تیم انجام شده است:

| مورد | وضعیت واقعی در محیط ما | تصمیم طراحی در کد |
| :--- | :--- | :--- |
| **دوربین** | Arducam B0495 USB3 روی `/dev/video1`؛ فقط خروجی خام `YUY2` (`960x600` و `1920x1200`) دارد و `MJPG` ندارد. | فشرده‌سازی `H.264` باید روی خود رزبری‌پای ۴ انجام شود و فقط رزولوشن‌های معتبر اجازه انتخاب دارند. |
| **شبکه و IP** | هات‌اسپات وای‌فای فعلی کند و ناپایدار است؛ کابل LAN و هات‌اسپات گوشی پایدارند و IP ممکن است عوض شود. | **ممنوعیت مطلق هاردکد کردن IP** در کد؛ همه‌چیز از فایل کانفیگ یا آرگومان خط فرمان خوانده می‌شود. |
| **اینترنت** | شبکه محلی تیم در آزمایشگاه یا زمین پرواز ممکن است به اینترنت وصل نباشد. | **ممنوعیت لینک‌های اینترنتی (CDN)**؛ تمام فایل‌های CSS، جاوااسکریپت و آیکون‌ها محلی داخل مخزن هستند. |
| **پورت‌های لپ‌تاپ** | پورت UDP `5000` روی ویندوز اشغال است. | استفاده از پورت‌های استاندارد MediaMTX (`8554` برای RTSP و `8889` برای WebRTC) با قابلیت تغییر در کانفیگ. |

## ۷. نقشه راه قدم‌به‌قدم (۱۰ ایستگاه تا سامانه نهایی)

ما کل پروژه را یک‌جا نمی‌سازیم؛ در هر قدم یک بخش کوچک و قابل اجرا می‌سازیم، کامل یادش می‌گیریم، تستش می‌کنیم و بعد به سراغ قدم بعدی می‌رویم:

- **قدم ۰:** ساخت اسکلت استاندارد پروژه پایتون با `uv`، تنظیم ابزارهای کیفیت کد (`ruff`, `ty`, `pytest`)، `.gitignore` و پایپ‌لاین CI.
- **قدم ۱:** راه‌اندازی `MediaMTX` روی لپ‌تاپ ویندوز، تنظیم فایروال و دیدن اولین تصویر آزمایشی در مرورگر با WebRTC.
- **قدم ۲:** اتصال دوربین واقعی روی رزبری‌پای، مقایسه عملی انکودر نرم‌افزاری (`x264enc`) و سخت‌افزاری (`v4l2h264enc`) از نظر مصرف CPU و تأخیر، و ارسال تصویر واقعی به لپ‌تاپ.
- **قدم ۳:** ساخت اولین صفحه وب اختصاصی خودمان (HTML + JavaScript) که با پروتکل WHEP تصویر زنده را پخش می‌کند.
- **قدم ۴:** ساخت سرور `Backend` با FastAPI در معماری شش‌ضلعی، مدیریت فایل کانفیگ معتبر با Pydantic و سرو کردن صفحه وب.
- **قدم ۵:** ساخت سرویس `Pi-Agent` روی رزبری‌پای برای مدیریت خودکار GStreamer، تشخیص کرش و ارتباط WebSocket با بک‌اند.
- **قدم ۶:** تغییر زنده رزولوشن، FPS و بیت‌ریت از داخل صفحه وب و بازگشت خودکار تصویر بدون نیاز به ترمینال.
- **قدم ۷:** نمایش آمار زنده حرفه‌ای روی تصویر (نرخ فریم واقعی، بیت‌ریت، تأخیر، گم‌شدن بسته‌ها و دما/مصرف پردازنده رزبری‌پای).
- **قدم ۸:** پایداری کامل در برابر قطع‌ووصل شبکه، اجرای خودکار هنگام روشن شدن رزبری‌پای (`systemd`) و راهکار آدرس‌دهی پایدار شبکه تیم.
- **قدم ۹:** امن‌سازی شبکه محلی (توکن احراز هویت ساده، CORS، خاموش شدن ایمن)، مستندسازی نهایی و راهنمای ادغام در ایستگاه کنترل زمینی XeroxUAV.
