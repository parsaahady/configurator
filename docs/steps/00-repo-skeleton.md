# قدم ۰: ساخت اسکلت استاندارد پروژه، ابزارهای کنترل کیفیت و CI

## ۱. هدف این قدم

در این قدم، اسکلت مهندسی پروژه را طبق استانداردهای تیم **XeroxUAV** می‌سازیم و چهار ابزار خودکار کنترل کیفیت کد (`uv`, `ruff`, `ty`, `pytest`) به همراه بازرس خودکار گیت‌هاب (`CI`) را راه‌اندازی می‌کنیم.

**کجای نقشه بزرگ هستیم؟** پیش از آنکه سراغ سرور ویدیو، دوربین و کدنویسی وب برویم، داریم «میز کار استاندارد» خودمان را آماده می‌کنیم تا از همین ابتدای مسیر، هر خط کدی که می‌نویسیم به‌طور خودکار از نظر ظاهر، نوع داده‌ها، پیچیدگی و درستی عملکرد بررسی شود.

## ۲. مفاهیم جدید (از صفر مطلق)

قبل از دیدن فایل‌ها، تمام اصطلاحات جدید این قدم را با مثال‌های ساده روزمره مرور کنیم تا هیچ کلمه‌ای برایت مبهم نباشد:

### گیت (`Git`)، شاخه (`Branch`) و کامیت استاندارد (`Conventional Commit`)
فکر کن `Git` یک دفترچه آزمایشگاهی مجهز به ماشین زمان است که تمام تغییرات پروژه را ثبت می‌کند.
- **شاخه (`Branch`):** شاخه اصلی پروژه `main` نام دارد و همیشه باید سالم و قابل اجرا بماند. وقتی می‌خواهیم قابلیت جدیدی بسازیم، یک «کپی پیش‌نویس» از آن می‌گیریم که به آن شاخه ویژگی (مثلاً `feat/step-00-repo-skeleton`) می‌گوییم. وقتی کارمان تمام و تست شد، آن را با شاخه اصلی ترکیب می‌کنیم.
- **کامیت استاندارد (`Conventional Commit`):** به هر نقطه ذخیره در گیت یک `Commit` می‌گوییم. در تیم ما، ابتدای پیام هر کامیت یک برچسب مشخص دارد تا تاریخچه پروژه تمیز و قابل فهم باشد؛ مثل `chore:` (کارهای زیرساختی)، `ci:` (تنظیمات تست خودکار سرور)، `docs:` (مستندات) و `feat:` (قابلیت جدید).

### فایل `.gitignore`
مثل فهرست وسایل ممنوعه هنگام بستن چمدان است! هر پوشه یا فایلی که نامش در `.gitignore` بیاید، گیت آن را نادیده می‌گیرد و روی اینترنت (GitHub) نمی‌فرستد؛ مثلاً پوشه‌های حجیم ابزارهای نصب‌شده یا فایل تنظیماتی که IP و رمز شبکه تو داخلش نوشته شده است.

### محیط مجازی (`.venv`)، مدیر بسته `uv` و فایل قفل (`uv.lock`)
- **محیط مجازی (`Virtual Environment` یا پوشه `.venv`):** تصور کن روی لپ‌تاپت دو پروژه مختلف داری؛ یکی نسخه قدیمی یک کتابخانه را می‌خواهد و دیگری نسخه جدیدش را. اگر همه کتابخانه‌ها را وسط سیستم‌عامل بریزی، پروژه‌ها خراب می‌شوند. پوشه `.venv` یک «جعبه ابزار اختصاصی و ایزوله» فقط برای همین پروژه است.
- **ابزار `uv`:** انباردار فوق‌سریع این جعبه ابزار است (جایگزین مدرن و ده‌ها برابر سریع‌تر ابزارهای قدیمی مثل `pip`). خودش پایتون و کتابخانه‌ها را پیدا و داخل `.venv` نصب می‌کند.
- **فایل `uv.lock`:** رسید دقیق شماره نسخه تک‌تک کتابخانه‌های نصب‌شده است. به لطف این فایل، وقتی پروژه را هم روی ویندوز لپ‌تاپ و هم روی لینوکس رزبری‌پای (`Python 3.13.5`) اجرا می‌کنی، دقیقاً نسخه‌های یکسانی نصب می‌شود.

### فرمت `TOML`، فایل `pyproject.toml` و چیدمان `src/`
- **فرمت `TOML`:** یک روش بسیار تمیز و خوانا برای نوشتن فایل‌های تنظیمات است که بخش‌های مختلف را با عنوان‌های داخل کروشه مثل `[project]` جدا می‌کند.
- **فایل `pyproject.toml`:** شناسنامه رسمی پروژه پایتون است. هم نام و نسخه پروژه را نگه می‌دارد و هم تنظیمات تمام ابزارهای کنترل کیفیت ما در همین یک فایل جمع شده است.
- **چیدمان `src/`:** قرار دادن کد اصلی داخل پوشه `src/real_time_cam/` باعث می‌شود پایتون کد ما را مثل یک پکیج واقعی و استاندارد ببیند و تست‌ها اشتباهاً فایل‌های متفرقه کنار پروژه را به جای پکیج اصلی بارگذاری نکنند.

### فرمت‌کننده و لینتر (`ruff`) و پیچیدگی کد (`McCabe`)
ابزار `ruff` مثل یک ویراستار سخت‌گیر و سریع است که دو کار انجام می‌دهد:
1. **فرمت‌کننده (`ruff format`):** ظاهر کد، فاصله‌ها و طول خط‌ها را یکدست و مرتب می‌کند.
2. **لینتر (`ruff check`):** کد را می‌خواند و ایرادهای منطقی، متغیرهای بلااستفاده و حتی **کدهای کامنت‌شده قدیمی** را پیدا می‌کند. یکی از مهم‌ترین قوانینش **پیچیدگی مک‌کیب (`McCabe Complexity`)** است که تعداد دوراهی‌های (`if / else / for`) داخل یک تابع را می‌شمارد. ما سقف آن را `8` گذاشته‌ایم تا همیشه مجبور شویم توابع کوچک، ساده و قابل فهم بنویسیم.

### نشانه‌گذاری نوع داده (`Type Hints`) و تایپ‌چکر ایستا (`ty`)
در پایتون معمولی اگر تابعی انتظار عدد داشته باشد و به اشتباه متن به آن بدهی، پایتون تا لحظه‌ای که برنامه به آن خط نرسد متوجه خطا نمی‌شود.
ما کنار ورودی و خروجی هر تابع برچسب نوع می‌گذاریم (مثلاً `-> str` یعنی خروجی حتماً متن است). سپس ابزار **`ty`** بدون اجرای برنامه، کل کد را مثل نقشه لوله‌کشی بررسی می‌کند تا مطمئن شود هیچ لوله‌ای به ورودی اشتباه وصل نشده است.

### تست واحد (`pytest`) و پوشش شاخه‌ای (`Branch Coverage`)
- **ابزار `pytest`:** برنامه‌ای است که توابع تست داخل پوشه `tests/` را اجرا می‌کند و با دستور `assert` («مطمئن شو که این شرط برقرار است») درستی کارکرد کد را می‌سنجد.
- **پوشش شاخه‌ای (`Branch Coverage`):** اندازه می‌گیرد چند درصد از مسیرها و دوراهی‌های کد ما توسط تست‌ها امتحان شده‌اند. طبق قانون تیم، این عدد همیشه باید **حداقل ۸۰٪** باشد وگرنه تست شکست می‌خورد.

### فرمت `YAML` و یکپارچه‌سازی مداوم (`CI` / `GitHub Actions`)
- **فرمت `YAML` (فایل‌های `.yml`):** فرمت متنی ساده‌ای برای نوشتن دستورالعمل‌ها که ساختار آن با تورفتگی (فاصله از اول خط) مشخص می‌شود.
- **سیستم `CI` (Continuous Integration):** یک بازرس خودکار روی سرورهای GitHub است. هر بار کد جدیدی روی GitHub بفرستی، یک کامپیوتر لینوکسی تمیز روشن می‌شود و طبق فایل `.github/workflows/ci.yml` هر چهار بررسی (`ruff format`, `ruff check`, `ty`, `pytest`) را از صفر اجرا می‌کند تا هیچ کد خرابی وارد شاخه اصلی تیم نشود.

## ۴. کد با توضیح خط‌به‌خط

بخش‌های مهم سه فایل کلیدی این قدم را بلوک‌به‌بلوک با هم بخوانیم:

### الف) فایل `pyproject.toml`

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```
این بخش به `uv` می‌گوید از ابزار استاندارد `hatchling` استفاده کند تا پوشه `src/real_time_cam` را مثل یک پکیج واقعی پایتون بسته‌بندی و داخل `.venv` نصب کند.

```toml
[project]
name = "real-time-cam"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = []
```
نام پروژه و حداقل نسخه پایتون (`3.11` به بالا) را مشخص می‌کند. چون روی رزبری‌پای تو `Python 3.13.5` نصب است، کاملاً با این شرط سازگار است و روی لپ‌تاپ هم با Python 3.11، 3.12 یا 3.13 بدون مشکل کار می‌کند. لیست `dependencies` فعلاً خالی است چون در هر قدم فقط کتابخانه‌ای را اضافه می‌کنیم که همان‌جا یادش می‌گیریم.

```toml
[dependency-groups]
dev = [
    "pytest>=8.3.0",
    "pytest-cov>=6.0.0",
    "ruff>=0.9.0",
    "ty>=0.0.1a0",
]
```
ابزارهایی که فقط هنگام توسعه و تست به آن‌ها نیاز داریم (و خود برنامه در زمان اجرا به آن‌ها وابسته نیست) در گروه `dev` قرار می‌گیرند. `pytest-cov` افزونه‌ای است که درصد پوشش تست را محاسبه می‌کند.

```toml
[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM", "C90", "N", "ARG", "ERA", "PLR"]

[tool.ruff.lint.mccabe]
max-complexity = 8

[tool.ruff.lint.pylint]
max-args = 5
max-branches = 6
max-returns = 4
max-statements = 30
```
اینجا دقیقاً قوانین کد تمیز تیم **XeroxUAV** را خودکار کرده‌ایم: مثلاً قانون `ERA` کد کامنت‌شده را رد می‌کند، `N` نام‌گذاری غیراستاندارد را می‌گیرد، `C90` پیچیدگی بالای `8` را مسدود می‌کند و بخش `pylint` اجازه نمی‌دهد تابعی بیشتر از ۳۰ خط یا ۵ ورودی داشته باشد.

```toml
[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = [
    "--strict-markers",
    "--strict-config",
    "--cov=real_time_cam",
    "--cov-branch",
    "--cov-report=term-missing",
    "--cov-fail-under=80",
]
```
به `pytest` می‌گوید هر بار اجرا شد، پوشش شاخه‌ای (`--cov-branch`) پکیج `real_time_cam` را اندازه بگیرد، خط‌های تست‌نشده را گزارش کند (`term-missing`) و اگر پوشش زیر ۸۰٪ بود (`--cov-fail-under=80`) با خطا توقف کند.

---

### ب) فایل `src/real_time_cam/__init__.py`

```python
from typing import Final

PACKAGE_VERSION: Final[str] = "0.1.0"
__version__: Final[str] = PACKAGE_VERSION


def get_package_version() -> str:
    return PACKAGE_VERSION
```
- `Final[str]` به تایپ‌چکر `ty` می‌گوید این متغیر یک **ثابت** است و هیچ کدی در هیچ جای برنامه حق ندارد مقدار `"0.1.0"` را تغییر بدهد (جلوگیری از اعداد و مقادیر جادویی پراکنده).
- `def get_package_version() -> str:` یک تابع پرس‌وجوی خالص (Query) است؛ هیچ وضعیتی را در سیستم عوض نمی‌کند و فقط یک رشته متنی (`str`) برمی‌گرداند.

### ج) فایل `tests/test_package_smoke.py`

```python
HEXAGONAL_LAYER_MODULES: tuple[str, ...] = (
    "real_time_cam.domain",
    "real_time_cam.application",
    "real_time_cam.infrastructure",
    "real_time_cam.presentation",
)


@pytest.mark.parametrize("module_path", HEXAGONAL_LAYER_MODULES)
def test_hexagonal_layers_are_importable(module_path: str) -> None:
    imported_module = import_module(module_path)
    assert imported_module.__name__ == module_path
```
- به جای نوشتن ۴ تابع تست تکراری برای ۴ لایه، از `@pytest.mark.parametrize` استفاده کردیم. این قابلیت به `pytest` می‌گوید: «همین یک تابع تست را ۴ بار، هر بار با یکی از نام‌های داخل `HEXAGONAL_LAYER_MODULES` اجرا کن».
- تابع `import_module` معادل دستور `import` پایتون است و بررسی می‌کند هر لایه معماری بدون خطا بارگذاری می‌شود.

## ۵. چه کاری باید بکنی

این دستورها را روی **لپ‌تاپ (در محیط Windows PowerShell)** داخل پوشه پروژه اجرا کن:

### مرحله ۱: اطمینان از نصب بودن `uv` (در PowerShell لپ‌تاپ)
ابتدا بررسی کن `uv` نصب است یا نه:

```powershell
uv --version
```

اگر نصب نبود، با همین یک دستور رسمی روی ویندوز نصبش کن و یک بار پنجره PowerShell را ببند و دوباره باز کن:

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

### مرحله ۲: ساخت محیط مجازی و نصب ابزارهای توسعه (در PowerShell لپ‌تاپ)

```powershell
uv sync --dev
```

**خروجی مورد انتظار:** ساخت پوشه `.venv` و نصب بسته‌های `pytest`, `pytest-cov`, `ruff`, `ty` و خود پکیج `real-time-cam` در چند ثانیه.

### مرحله ۳: اجرای چهار بررسی کیفیت کد (در PowerShell لپ‌تاپ)

```powershell
uv run ruff format --check .
uv run ruff check .
uv run ty check
uv run pytest
```

**خروجی مورد انتظار (که در محیط تست ما هم دقیقاً اجرا و تأیید شد):**
- دستور اول: `13 files already formatted`
- دستور دوم: `All checks passed!`
- دستور سوم: `All checks passed!`
- دستور چهارم (`pytest`):
  ```text

  tests/test_package_smoke.py .....                                        [100%]
  ...
  Required test coverage of 80% reached. Total coverage: 100.00%
  ============================== 5 passed ==============================
  ```

*(نکته: در این قدم هنوز نیازی به رزبری‌پای و دوربین نیست؛ اما هر زمان پروژه را در `~/projects/real_time_cam` روی رزبری‌پای کلون کنی، همین ۴ دستور دقیقاً روی `Python 3.13.5` رزبری‌پای هم اجرا می‌شوند.)*

## ۶. اگر خطا دیدی

۱. **خطای `uv : The term 'uv' is not recognized as the name of a cmdlet` در PowerShell:**
- **معنی:** ویندوز هنوز مسیر برنامه `uv` را در متغیر `PATH` پیدا نکرده است.
- **راه‌حل:** بعد از نصب `uv`، حتماً پنجره PowerShell را کامل ببند و یک پنجره جدید باز کن تا مسیر جدید بارگذاری شود.

۲. **خطای `running scripts is disabled on this system` در ویندوز:**
- **معنی:** سیاست امنیتی پیش‌فرض PowerShell اجازه اجرای اسکریپت‌های `.ps1` (مثل فعال‌سازی دستی `.venv\Scripts\activate.ps1`) را نمی‌دهد.
- **راه‌حل:** اصلاً نیازی به اجرای `activate` نداری! همیشه دستورها را با پیشوند `uv run ...` اجرا کن؛ خود `uv` مستقیماً از پایتون داخل `.venv` استفاده می‌کند و به این خطا نمی‌خوری.

۳. **خطای فرمت در `uv run ruff format --check .` روی ویندوز:**
- **معنی:** ممکن است گیت روی ویندوز کاراکتر پایان خط فایل‌ها را عوض کرده باشد یا فایلی را ویرایش کرده باشی.
- **راه‌حل:** دستور `uv run ruff format .` (بدون `--check`) را اجرا کن تا خودکار همه فایل‌ها را استاندارد کند؛ همچنین یک بار دستور `git config --global core.autocrlf input` را بزن.

۴. **خطای `Author identity unknown` هنگام `git commit`:**
- **معنی:** هنوز نام و ایمیلت را به گیت معرفی نکرده‌ای.
- **راه‌حل:** این دو دستور را با نام و ایمیل گیت‌هاب خودت اجرا کن:
  ```powershell
  git config --global user.name "Your Name"
  git config --global user.email "your_email@example.com"
  ```

## ۷. خودت را بسنج

قبل از رفتن به قدم بعدی، به این ۳ مورد فکر کن یا امتحانشان کن:

۱. **سؤال مفهومی:** چرا پوشه `.venv/` را داخل `.gitignore` گذاشتیم تا وارد گیت نشود، اما فایل `uv.lock` را حتماً داخل گیت ذخیره می‌کنیم؟
۲. **آزمایش عملی کوچک:** فایل `src/real_time_cam/__init__.py` را باز کن، در آخر آن یک خط کد کامنت‌شده مثل `# old_value = 42` بنویس و دستور `uv run ruff check .` را اجرا کن. ببین کدام قانون (`ERA001`) مچ آن را می‌گیرد! *(در پایان، آن خط اضافه را پاک کن تا چک‌ها دوباره سبز شوند.)*
۳. **سؤال معماری:** طبق توضیحی که در `src/real_time_cam/domain/__init__.py` نوشتیم، آیا در قدم‌های بعدی اجازه داریم داخل پوشه `domain/` کتابخانه وب `fastapi` را `import` کنیم؟ چرا؟

## ۸. چه چیزی یاد گرفتیم + قدم بعدی

**خلاصه این قدم:**
یاد گرفتیم چطور یک پروژه پایتون مدرن را با `uv` و چیدمان `src/` بسازیم، چهار لایه معماری شش‌ضلعی (`domain`, `application`, `infrastructure`, `presentation`) را ایجاد کنیم و چهار نگهبان خودکار کیفیت کد (`ruff format`, `ruff check`, `ty`, `pytest`) را هم روی سیستم خودمان و هم در `GitHub Actions` فعال کنیم.

**در قدم ۱ چه می‌کنیم؟**
وارد مسیر ویدیو می‌شویم! برنامه **MediaMTX** را روی لپ‌تاپ ویندوز راه‌اندازی می‌کنیم، فایروال ویندوز را تنظیم می‌کنیم، با یک پایپ‌لاین آزمایشی GStreamer تصویر رنگی تست (`videotestsrc`) را با فرمت `H.264` به آن می‌فرستیم و **اولین تصویر زنده WebRTC را داخل مرورگر وب** تماشا می‌کنیم!
